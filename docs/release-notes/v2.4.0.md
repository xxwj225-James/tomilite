# TomiLite v2.4.0

**Since v2.3.0** — a migration, a feature, and the corrections that came out of auditing two things that had never been audited: what clock a stored timestamp is on, and what counts as a task. Chinese transcripts come back in the script you choose, and your database ends up on one clock instead of two.

## ✨ Features

- **Chinese transcripts are written in the script you choose.** whisper has no simplified/traditional switch — its only Chinese token is `<|zh|>`, so `-l zh` means "Chinese" and the model picks the orthography. The bundled model picks Traditional, and a Mandarin meeting came back with every differing character in Traditional (`認為`, `發布會`, `會不會`). Settings → Meetings now has a **Chinese script** choice — Simplified / Traditional / Don't convert, default **Simplified** — applied to the finished transcript.
  - **It changes the characters, not the words.** The conversion is a dictionary pass over the transcript, so nothing about the decoding changes: the same audio gives the same reading, in the other script. It only runs for Chinese, decided by the language whisper _detected_, and `Don't convert` is there for anyone who wants exactly what the model produced.
  - **`--prompt` was tried first and thrown away.** An initial prompt does flip the script, but it primes the whole decoder rather than selecting an orthography: across four runs of one file it also changed the _words_ — the speaker's name came out three different ways, none of them correct — and added punctuation that was not in the audio. Trading accuracy for character shapes is the wrong trade.
  - **It applies to the next transcription**, including re-transcribing a meeting you already have. Existing transcripts are not rewritten: they were produced under the old behaviour, and silently editing stored text is worse than leaving it.
- **The speech model is no longer something you are asked about.** Settings → Meetings now shows **one** row — Base, with install and delete — and no model name appears in the recorder, the editor or the transcript. TomiLite transcribed with `base` all along; the pickers asked you to choose between four models whose differences you had no way to judge, and explaining the resulting fallback took three separate warnings. A setting that needs three warnings to be honest about itself is one that should not have been yours to set.
  - **A substitution is no longer recorded as your request.** When the requested model was not on disk, `pickModel` fell back to the smallest installed one and then wrote that substitute into the meeting's `whisperModel` — the column holding what you asked for. So a meeting became pinned to whatever happened to be installed the day you recorded it: the intent was gone, and downloading the model you actually wanted later had no effect on it. The outcome now goes to `transcribeModel`, always, and `whisperModel` is written as the constant.
  - **Nothing is transcribed by a model you cannot install.** `base` is used whenever it is on disk; only a machine with _no_ `base` falls back to the smallest model it does have, so an older download keeps working instead of the app declaring no model installed. Those older models are listed under **Other models on this machine** with a delete button — previously they occupied 78 MB–1.5 GB with nothing in the UI to remove them.

## 🐛 Fixes

- **The Home task card never loaded its numbers.** It requested `\api\health.taskStats`, and in a JavaScript string neither `\a` nor `\h` is an escape — so the request went to a path spelled `apihealth.taskStats`, which cannot return JSON. The wrong path was there from the first commit and the card has been blank in every build shipped so far. It now asks for the real endpoint, and it re-reads it whenever Home comes back on screen — panels are hidden rather than unmounted, so "mounted" is not a refresh signal, which is why completing a task and returning to Home showed you the figures from app start.
  - **It has a refresh button of its own**, which it was the only card on that page to lack, with a spin while the request is in flight.
  - **It no longer hides itself when the board is empty.** With zero tasks it shows the four figures at zero, refresh button included, instead of leaving a blank where the card used to be — and the endpoint no longer answers with a second payload shape for that case (`done / 0` is `NaN`, and `NaN` leaves the API as `null`).
- **Home and the task board cannot drift apart again.** They agreed when this was audited — 109 tasks, 54 done, both places — so what follows is three latent disagreements closed rather than a visible number being corrected.
  - **The agent counted the table, not the tasks.** `get_stats` ran four unfiltered `count()` calls, so it included the `type: 'email'` rows the Email panel mirrors into `Issue` and the `cancelled` rows the board has no column for, and never folded `in_review` into in-progress. Asked for the task count it answered **144 tasks, 63 done** while the Home card two inches away said 109 and 54. It now goes through the same definition as everything else: **109 / 45 / 10 / 54**.
  - **The tab badges were counted over 200 rows, not over the tasks.** `issue.list` is capped at 200, and the board counted its badges from the array it had fetched. Below 200 rows that is exactly right; above it the badges under-report while still looking reasonable. They are now counted in SQL over the whole set (`issue.taskCounts`) and render as nothing until the count arrives, rather than as a plausible wrong number.
  - **Standup's "done yesterday" could never include the morning.** The cutoff was built with `toISOString()` and compared against stamps stored as `YYYY-MM-DD HH:MM:SS`. Those differ at character 10 — a space (0x20) against `T` (0x54) — so any row sharing the cutoff's date prefix sorted before it, and the first eight hours of the local day were unreachable. No rows happened to fall in that window, so it was never seen; it is fixed rather than left for the day it is.
  - **The agent's `list_issues` tool was the last caller counting the whole table.** Asked to list what is on your plate it handed over the mailbox rows the Email panel mirrors into `Issue` — and its projection carries no `type` field, so the model had no way to tell a newsletter from a task. Every other counter already used the shared definition; this one now does too.
- **The email list showed the wrong arrival time.** An email's `Date:` header is stored in UTC, and both the list and the detail view printed it by slicing the raw text, so every row read 8 hours earlier than it arrived at UTC+8. A mail received at 09:30 was shown as 01:30. Both now render it in your own time zone.
- **"Show the consent notice again" works now.** It only flipped a flag in the meeting panel, while both the date in Settings and the recorder's gate read the stored row — so the click changed the one thing you could not see, the date never moved, and a reload brought it back. It now clears the stored row and the date changes on the spot. Per-meeting consent records are deliberately left alone: they are the audit trail of consent actually given for a recording.
- **Chat messages save again.** The message write asked the database for a column `ChatMessage` does not have — `updatedAt`, where the model keeps only `createdAt` — and Prisma rejects the whole call when it is handed a field the model lacks, so _every_ save was refused: a sent message stayed on screen until the next reload, and was gone after it. Nothing surfaced the error, because the caller swallows it. One flow turned that into real loss: compressing a session deletes its rows and then writes back the summary and the last few messages, so a session compressed while saves were broken — auto-compression fires on its own at 85% of the context window, no click needed — came back empty. That is how one session lost its history. This fix does not restore what was already lost, and it changes nothing about the messages that are still stored.
- **The action-items tab no longer asks you to run the minutes you just ran.** It had a single sentence for every way that list can be empty, and it fitted only one of them: "TomiLite looks for them when it writes the minutes" is an invitation to _generate_ minutes, and it stayed on screen after the run that found none. Finding none is a normal outcome — the model is asked for concrete assignable actions, never topics, and "Empty arrays are correct when the meeting decided or assigned nothing" is in the prompt — so a 30-second clip that decided and assigned nothing ends _done_ with zero rows, and the tab said nothing had been analysed. It now reads `aiStatus` and shows one of four: not run yet (the invitation), generating, done with none found, failed. The count itself is still never rendered as `0 action items`.
- **Settings → Meetings could not read its own settings back.** The tab fetched `meeting.defaults` and read `.value` off the response, but `system.getConfig` returns the stored string itself — so the value was always `undefined`, the recording-defaults card rendered its built-in defaults forever, and **every edit wrote those defaults back over the fields you had already set**: set the language, change the retention days, and the language was silently `auto` again. The read now matches what the endpoint returns.

## ⚠️ Notes

- **This release migrates your database**, on first launch, once. Timestamps used to be written by two different clocks into the same columns — the database default, which stores local time, and ~26 code paths that store UTC — and nothing in the stored text said which one a given row had. The practical effect was small but visible: task dates could be off by a day, and a handful of rows were. On start-up the app now converts the affected rows in thirteen tables (`Issue`, `ChatSession`, `KnowledgePage`, `McpServer`, `Report`, `ChatMessage`, `GitCommit`, `KnowledgeCache`, `UserHealthSnapshot`, `McpAuditLog`, `AiDecisionFeedback`, `FocusSession`, `SmartEmail`), and rebuilds `Issue` to change its column defaults — SQLite cannot alter a default in place, so that one table is copied into a new one and swapped. Rows, comments, changelogs, board cards, linked emails and the search index all survive it; the migration verifies its own row counts and inbound references before it commits, and does nothing at all if it cannot. It writes its own marker, so it runs once and never re-runs. A database created by this version is already UTC and is left alone.
  - **Some columns were not merely a display problem.** Four of the tables above drive caches and windows that compare a stored stamp against a UTC cutoff — the health snapshot, the knowledge cache, the self-learning feedback window, the MCP pending-approval filter — so the 8-hour skew silently widened each of them. Those are now the right width.
  - **A few rows were genuinely undecidable and were left as they are.** Where a row's two stamps differ by less than your UTC offset, the stored text cannot say whether that was a local-time edit minutes later or a UTC edit hours later. Four rows in a real database fall in that band. They are counted and reported in the log rather than converted on a guess.
  - **`GitCommit.timestamp` is also normalised**, from `2026-07-16T15:05:46+08:00` to the same shape every other timestamp column uses. Every commit keeps the instant it had.
  - **`Meeting`'s timestamps stay local, deliberately**, as does `ApiKey.createdAt`. Their writers and their readers agree on local time, which makes them consistent columns rather than mixed ones — the defect was two clocks in one column, not one clock that is not UTC. `Report`, which really was mixed, is converted above.
  - **A new session no longer inherits the clock from the default.** `createSession` passed only a title and let the column stamp both of its timestamps in local time while every later write was UTC — one column, two clocks, and it sorted a brand-new empty session ahead of real ones. It was listed under known issues in the previous release and is fixed here.
  - **It assumes your machine's time zone has not changed since those rows were written** — the conversion reads local time using the current zone. If you have moved time zones, or you are carrying a database from another machine, the affected rows can end up off by the offset. Take a copy of `~/.tomilite/dev.db` before the first launch of this version if that matters to you.
- **`Meeting` gains one column**, `transcribeModel`, at `SCHEMA_VERSION` 23 → 25 — a plain additive `ALTER TABLE`, so no table is rebuilt and no row is touched. (The counter skips 24: only 23 shipped, and the steps in between are additive.) Existing meetings keep their `whisperModel` and read `null` for the new column, which is the honest value: for a meeting transcribed before this version, which model ran is genuinely unknowable, and nothing back-fills a guess.
- **The schema step no longer reports a success it did not have.** `prisma db push` cannot run against a database carrying the search index — `global_fts` and `embed_queue` are objects Prisma does not model — and on those installs it used to fail on every launch and be recorded as applied anyway, which made the whole step a no-op that looked like it had worked. It is skipped when the index is present, and a push that fails now leaves the version unstamped and writes its error down instead, so the next launch retries rather than skipping.
- **A meeting transcribed before this version keeps its transcript**, in whichever script the model produced. Re-transcribing it applies the setting.
- **`opencc-js` is a new dependency** of the API (`apps/api/package.json`). It inlines its conversion dictionaries, so it adds no file reads and no network access, and it survives the API being bundled into a single file.
