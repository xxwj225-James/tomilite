# TomiLite v2.7.0

**Since v2.6.0** — note import can now read 印象笔记 again, because 印象笔记 stopped writing the file TomiLite could read. The app's Windows client no longer offers `.enex`; its own support line says to export `.notes` instead, and the export menu offers `.notes`, `.html` and `.mht`. The one import path named after that app was, by then, the one file its users could not produce. `.html` and `.mht` are both supported now, both parsed in the renderer with no new dependency, and `.enex` is kept for everyone whose client still writes it.

## ✨ Features

- **Import 印象笔记's HTML export.** Pick the folder it exported, not the files inside it: every `.html` / `.htm` becomes a note, and its images are read from the `_files` folder sitting beside it — which is why a file pick would bring none of them. Each note is filed under the exported folder's name (`.notes` infix stripped, so `Travel.notes.html` lands in `Travel`).
- **Import 印象笔记's `.mht` export.** One file holds the note, its images and its attachments, so a multi-file pick is complete on its own — the same shape as `.enex`. Images are embedded the way the `.enex` import embeds them, and character encodings, quoted-printable and RFC 2047 headers are all decoded, so a Chinese title arrives as Chinese rather than as `=?GB2312?B?…?=`.
- **Re-importing the same export skips what is already there**, for both new formats, exactly as it does for Markdown and `.enex`. Renaming a note *inside TomiLite* does not create a second copy: an HTML note's identity is the file it came from, not its title.

## 🔧 Changes

- **The `.enex` section is now labelled with the app that writes the format**, and says outright that 印象笔记 7.x no longer produces it. "印象笔记 export file (.enex)" pointed every 印象笔记 user at a file their client cannot export, which is a worse failure than a missing feature — it is a wrong instruction.
- **A folder picker is back in the import dialog — for the HTML export only.** Markdown lost its folder pick in v2.6.0 on purpose (a folder drags in hundreds of files that are not notes, and all you get for it is a large "ignored" count). The HTML export is the opposite case: those files *are* the payload. Markdown is unchanged.
- **One HTML file is one note, and you will be told if that is not what you had.** If a single file contains more than one note divider, the summary says how many — it does not split them. Splitting needs a test that tells a note boundary apart from the empty anchors a clipped web page is full of, and that test is not provable on the export we have. A test that is wrong does not degrade the import; it shreds a notebook into fragments each with an invented title and id.
- **Two new size limits.** 32 MB per note file (an HTML file that size is a whole notebook exported as one page, and is refused rather than turned into a 32 MB note), 100 MB per `.mht` — the same number as `.enex`, since both are one file carrying one note's resources.
- **Tasks and reports are back on the knowledge map, below the tree.** The block is called the project pulse: todo / in progress / done counts, the last three finished tasks and the last three reports, each one a click away from its own panel. The map itself still holds notes only — a leaf *is* a note id, and with a task in its place everything the map does with a leaf (open the note, follow a `[[link]]`, find its semantic neighbours) stops working. But the card this map replaced read **tasks, notes and reports**, and keeping only the notes described a narrower project than the one you have. So they sit beside the tree instead of in it, using the task board's own status words and the same counting logic — the Home card, the board's badges and this strip cannot report three different numbers.
- **Web search works again with your proxy switched off.** Windows clears `ProxyEnable` when a proxy is turned off but leaves the address in `ProxyServer`, and TomiLite read the address without reading the switch — so every search went to a port with nothing listening and came back an empty result list, which reads as "no matches" rather than as unreachable. The system proxy is now read as the three registry values it is: the switch, the address, and the bypass list. The bypass list is honoured, so a *working* proxy no longer intercepts the intranet host you excluded, and a proxy that never connects is retried direct instead of taking the turn down with it.

## ⚠️ Notes

- **No new dependency.** The MIME container parser is about 200 lines in this repo, walked as bytes rather than text, because the WHATWG encoding standard aliases `iso-8859-1` to windows-1252 and a decoder that mangles every byte in `0x80`–`0x9F` is not a decoder you can split a container with.
- **These two parsers are verified against one real export, and it holds one note.** The format was documented from a single 3374-byte `.html` and its 820 KB `.mht` twin. What that sample *did* establish is recorded in the code: there is no `<en-note>` container, the note divider is a self-closing `<a name="…"/>`, the `<title>` is the format's own `Evernote Export` on every file (so it is refused as a title rather than given to every note), image references are plain relative paths carrying a `?t=attachment` query, and there is no per-note date anywhere — so imported notes take the import time rather than a timestamp that was really the moment the export ran. What one sample *cannot* establish is whether a single-page export really is one file per notebook, and whether an export ever carries a per-note title. Both are handled the cautious way rather than the clever way, and both are written down where the next person will find them.
- **`.notes` is not supported.** It is an encrypted private format with no published specification and no third-party parser; the migration route the community uses for it is `evernote-backup --backend china`, which produces `.enex` — which TomiLite already reads.
- **Import is not a backup.** Following a note's `sourceId` means an import can update a note you have edited in TomiLite (tick **Overwrite**), and it means a note *deleted* in TomiLite comes back on the next import of the same file. Import is one-way, by design.
