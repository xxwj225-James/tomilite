# TomiLite v2.4.0

**自 v2.3.0 起** —— 一次迁移、一个新功能,以及两件此前从未被审计过的事情查出来的修正:一个存储的时间戳属于哪个时钟,以及什么才算一个任务。中文转写字形由你决定,数据库从两个时钟收敛成一个。

## ✨ 新功能

- **中文转写字形由你决定。** whisper 根本没有简繁开关 —— 它关于中文的全部词汇就是一个 `<|zh|>` token,所以 `-l zh` 的意思是「中文」,字形由模型自选,而内置模型选的是繁体：一段普通话录音里每一个有简繁差异的字都回来了（`認為`、`發布會`、`會不會`）。设置 → 会议现在有**中文转写字形**一项 —— 简体中文 / 繁體中文 / 不转换，默认**简体中文**，作用在转写结果上。
  - **改的是字形，不是用词。** 转换是对转写结果做一遍字典替换，解码过程一点没动：同一段音频读出来还是同一句话，只是换了写法。它只对中文生效，判断依据是 whisper **检测到的**语言；「不转换」是给想要模型原始输出的人留的。
  - **`--prompt` 试过，放弃了。** 初始提示词确实能翻转字形，但它启动的是整个解码器，不是在选字形：同一个文件跑四次，**用词也跟着变了** —— 说话人的名字出现了三种写法，没有一种是对的 —— 还多出了音频里没有的标点。拿转写的准确性去换字形，是笔亏账。
  - **对下一次转写生效**，包括重新转写一场已有的会议。已有文字稿不会被改写：那是在旧行为下产生的，偷偷去改存下来的文本比留着更糟。
- **语音模型不再需要你来决定。** 设置 → 会议现在只有**一行** —— Base，带安装和删除按钮；录音条、会议编辑器、文字稿里都不再出现任何模型名。TomiLite 一直就是用 `base` 转写的：那套选择器要你在四个模型之间做选择，而它们的差别你无从判断，解释由此产生的回退又额外花了三条警告。一个需要三条警告才能自圆其说的设置，本来就不该交给你设。
  - **「替代」不再被当成你的请求记下来。** 当请求的模型不在本地时，`pickModel` 会退回到已安装中最小的那个，然后把替代值**写回**会议的 `whisperModel` —— 也就是存放「你要求了什么」的那一列。于是一场会议就被永久钉死在录音当天恰好装着的那个模型上：意图没了，而且之后下载了你真正想要的那个模型对它也毫无作用。现在实际结果一律记在 `transcribeModel`，`whisperModel` 写常量。
  - **不会再有你装不上的模型替你转写。** 只要 `base` 在本地就用 `base`；只有**完全没有** `base` 的机器才会退回到它确实有的最小模型，这样旧版本的下载仍能工作，而不是被告知「没有安装模型」。这些旧模型列在**本机上的其他模型**一栏并带删除按钮 —— 它们此前占着 78 MB–1.5 GB，界面上却没有任何地方能删掉。

## 🐛 修复

- **首页的任务统计卡片从来没读到过数字。** 它请求的是 `\api\health.taskStats`,而在 JavaScript 字符串里 `\a` 和 `\h` 都不是转义符 —— 于是这个请求打到了一个拼作 `apihealth.taskStats` 的路径上,不可能返回 JSON。这个错路径从首次提交起就在那里,到目前为止发布过的每一个版本里那张卡片都是空的。现在它请求真实的接口,并且在每次回到首页时重新读一次 —— 面板是隐藏而不是卸载,所以「挂载」不是刷新信号,这也是为什么完成一个任务再回到首页,看到的还是启动时的数字。
  - **卡片上补了一个刷新按钮**,那一页的卡片里只有它没有,请求进行中会转圈。
  - **任务板为空时它不再把自己藏起来。** 一个任务都没有时,它把四个数字显示成 0(刷新按钮照旧在),而不是留下一块空白;接口也不再为这种情况换一种载荷形状(`done / 0` 是 `NaN`,而 `NaN` 出接口时会变成 `null`)。
- **首页与任务看板不会再各说各话。** 本次审计时两处数字是一致的 —— 都是总数 109、已完成 54 —— 所以下面修的不是某个看得见的错数，而是三条**潜在**的分歧路径。
  - **Agent 数的是整张表，不是任务。** `get_stats` 发了四次不带过滤的 `count()`，于是把邮件面板镜像进 `Issue` 的 `type: 'email'` 行、以及看板上根本没有列的 `cancelled` 行都算了进去，并且从不把 `in_review` 折进「进行中」。问它有多少任务，它答**144 个任务、63 个已完成**，而两英寸外的首页卡片写的是 109 和 54。现在它与其他所有调用方走同一个定义：**109 / 45 / 10 / 54**。
  - **页签徽章数的是 200 行，不是全部任务。** `issue.list` 上限 200 行，而看板是拿**已取回的那个数组**去算徽章的。行数在 200 以内时这完全正确；超过之后徽章就会少报，而且看起来仍然合理。现在改为在 SQL 里对全集计数（`issue.taskCounts`），并且在计数到达之前渲染为**空**，而不是一个看似合理的错数。
  - **晨会的「昨天完成」永远包含不了上午。** 截止时间是 `toISOString()` 造的，而比较的是 `YYYY-MM-DD HH:MM:SS` 形状的存储值。两者在第 10 个字符上就不同 —— 一个是空格（0x20），一个是 `T`（0x54）—— 于是任何与截止时间共享同一日期前缀的行都会排在它前面，当地一天的头八个小时**永远落不进窗口**。恰好没有行落在那个区间，所以从没被看见；这次是直接修掉，而不是留着等那天到来。
  - **Agent 的 `list_issues` 工具是最后一个数整张表的调用方。** 让它列出你手头有什么，交出来的却是邮件面板镜像进 `Issue` 的邮箱行 —— 而且它的返回结构里根本没有 `type` 字段，模型连「这是邮件不是任务」都无从判断。其他所有计数器早就走共享定义了，现在它也走。
- **邮件列表显示的到达时间是错的。** 邮件的 `Date:` 头按 UTC 存储，而列表和详情都直接截取原文本显示 —— UTC+8 下每一行都比实际到达时间早 8 小时：9:30 收到的邮件显示成 1:30。现在两处都按你所在的时区渲染。
- **「重新显示声明」现在真的有用。** 它过去只在会议面板里翻了一个标志位，而设置页显示的日期和录音的准入判断读的都是存储里的那一行 —— 于是这一下点击改的是你看不见的地方，日期不动，刷新一下又回来了。现在它会清掉存储里的那一行，日期当场变化。每场会议各自的确认记录**故意不动**：那是「这场录音当时确实确认过」的审计记录。
- **聊天消息又能存下来了。** 写消息时向数据库要了一个 `ChatMessage` 根本没有的列 —— `updatedAt`,而这个模型只有 `createdAt` —— Prisma 遇到模型里不存在的字段会拒绝整条写入,于是**每一次保存都失败**:发出去的消息留在屏幕上,一刷新就没了。调用方把这个错误吞掉了,所以界面上什么都看不出来。其中一条流程会把它变成真正的丢失:压缩上下文是「先删后写」—— 先删掉该会话的全部消息,再写回摘要和最近几条 —— 所以在保存坏掉期间被压缩过的会话(上下文到 85% 时会自动压缩,不需要你点)会变成空的。这次有一个会话就是这样丢掉了历史。本修复不会找回已经丢失的内容,也不改动仍存着的消息。
- **行动项页签不再催你去生成你刚生成过的纪要。** 它原本用一句话覆盖了这个列表为空的每一种情况，而那句话只适用于其中一种：「生成纪要时 TomiLite 会从中提取」是在邀请你**去**生成纪要，可它在那次「生成了、但没找到」之后依然留在原处。「没找到」本来就是正常结果 —— 提示词要的是具体可指派的事、从不接受话题，而且里面写着「会议没有决定或指派任何事时，空数组就是正确答案」—— 所以一段什么都没决定、也没指派的 30 秒片段会以 `done` 结束、零行，而页签却说得像还没分析过。现在它读 `aiStatus`，在四种状态里选一种显示：还没生成（那句邀请）、正在生成、已生成但没有、生成失败。条数本身依然不会渲染成「0 个行动项」。
- **设置 → 会议读不回自己存下的设置。** 这个标签页取 `meeting.defaults` 时按 `.value` 去读，而 `system.getConfig` 返回的就是那个字符串本身 —— 于是拿到的永远是 `undefined`，录音默认值卡片一直显示内置默认值，而且**每一次修改都会把这些默认值写回去，盖掉你已经设过的字段**：设了语言，再去改保留天数，语言就悄悄变回 `auto` 了。现在按接口真实的返回形状读。

## ⚠️ 说明

- **本次发布会迁移你的数据库**，首次启动时执行一次。此前的同一个时间字段由两个时钟写入 —— 数据库默认值存的是本地时间，而约 26 处代码存的是 UTC —— 且存的文本本身看不出某一行是哪个。实际影响不大但看得见：任务日期可能差一天，而且确实有若干行差了。现在启动时会把受影响的十三张表（`Issue`、`ChatSession`、`KnowledgePage`、`McpServer`、`Report`、`ChatMessage`、`GitCommit`、`KnowledgeCache`、`UserHealthSnapshot`、`McpAuditLog`、`AiDecisionFeedback`、`FocusSession`、`SmartEmail`）统一转成 UTC，并重建 `Issue` 以改掉它的列默认值 —— SQLite 不能原地改默认值，所以这张表是整表复制后替换的。行数、评论、变更记录、看板卡片、关联邮件和搜索索引都会保留；迁移在提交前会自校验行数与入站引用，做不到就什么都不做。它会写下自己的标记，只跑一次、不再重跑。本版本新建的数据库本来就是 UTC，不会被碰。
  - **其中几列不只是显示问题。** 上表有四张驱动缓存或时间窗，拿存储的时间戳与 UTC 截止时间比较 —— 健康快照、知识缓存、自学习反馈窗口、MCP 待审批过滤 —— 8 小时偏差让它们各自悄悄变宽了。现在宽度是对的。
  - **有少数行确实无法判定，保持原样。** 当一行的两个时间戳相差小于你的 UTC 偏移量时，存的文本无法说明那是「几分钟后的本地时间修改」还是「几小时后的 UTC 修改」。真实数据库里有 4 行落在这个区间。它们被计数并写进日志，而不是凭猜测转换。
  - **`GitCommit.timestamp` 也做了形状归一**，从 `2026-07-16T15:05:46+08:00` 转成其他时间列统一的形状。每条提交的时间点不变。
  - **`Meeting` 的时间戳有意保持本地时间**，`ApiKey.createdAt` 同理。它们的写入方与读取方对本地时间是一致的，属于自洽的列而非混合的列 —— 缺陷是「一列里两个时钟」，不是「某个时钟不是 UTC」。真正混合的 `Report` 已在上方一并转换。
  - **新建会话不再沿用默认值的时钟。** `createSession` 只传了标题，让列默认值把两个时间戳都按本地时间写下去，而之后每一次写入都是 UTC —— 一列两个时钟，而且会让一个刚建的空会话排到真实会话前面。它在上一个版本里列在「已知问题」中，这次修掉了。
  - **它假设这些行写入之后你的机器时区没有变过** —— 转换是按当前时区理解本地时间的。如果你换过时区，或这份数据库来自另一台机器，受影响的那些行会整体偏移一个时区差。若你在意，建议首次启动本版本前先备份 `~/.tomilite/dev.db`。
- **`Meeting` 新增一列** `transcribeModel`，位于 `SCHEMA_VERSION` 23 → 25 —— 一条纯加性的 `ALTER TABLE`，不重建任何表、不触碰任何行。（计数跳过了 24：对外只发布过 23，中间那些步都是加性的。）已有会议保留其 `whisperModel`，新列读出 `null`，而这正是诚实的取值：本版本之前转写过的会议，当时跑的是哪个模型是真的无从得知，也没有任何地方会补一个猜测进去。
- **schema 这一步不再汇报一个它并没有的成功。** `prisma db push` 在带着搜索索引的数据库上跑不了 —— `global_fts` 和 `embed_queue` 是 Prisma 没有建模的对象 —— 而在这些安装上它过去每次启动都会失败、却仍被记为「已应用」，于是整个这一步变成一个看起来成功的空操作。现在检测到索引存在就跳过；推送失败则不再写版本号，而是把错误记下来，让下次启动重试，而不是跳过。
- **本版本之前转写过的会议保留原文字稿**，是模型当时写出的字形。重新转写一次即会应用该设置。
- **`opencc-js` 是 API 新增的依赖**（`apps/api/package.json`）。它的转换字典是内联的，不读文件、不联网，因此接口被整体打包成单文件后依然可用。
